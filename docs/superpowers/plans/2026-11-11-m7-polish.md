# SecureDB Vault — Milestone 7 (Polish) Plan

**Goal:** AWS KMS key provider, demo data, documentation and repository polish.
**Spec:** §2.4 (AwsKmsKeyProvider), §4.3 (`seed-demo`), §7 (docs, ADRs, SECURITY, LICENSE, README).
**Builds on:** M6 (`feat/m6-console`), branch `feat/m7-polish`. This branch also carries the
fixes from the M6 review.

## Decisions

| # | Decision | Why |
|---|---|---|
| P1 | KMS provider takes an injected client and is tested against an in-memory fake, not `moto`; `boto3` is an optional extra (`securedb[kms]`) | Keeps the default install and test run free of a large cloud SDK; the provider is ~40 lines over two KMS calls. Spec said `moto`. |
| P2 | Wrap context is passed as the KMS encryption context | KMS itself then refuses a wrong-tenant unwrap, and CloudTrail records the context. |
| P3 | `seed-demo` prompts for the demo console password and prints API keys and TOTP links once | No default credentials anywhere in the repository. |
| P4 | CI coverage gate widened to `crypto`, `vault`, `policy`, `audit` (>= 90%) | Spec §6. |

## Review outcome

Fresh review of the code and of every checkable claim in the docs: 0 Critical, 5 Important (all fixed, code fixes test-first), 13 Minor, 11 documentation inaccuracies (all corrected).

Fixed:
1. KMS calls had no timeouts and `/readyz` called KMS on every probe: the client now has short timeouts and bounded retries, and readiness is cached for 30 s. Required IAM actions are documented.
2. Every KMS failure became a silent 500 indistinguishable from tampering: outages, throttling and access errors are now 503 (`KeyProviderLocked`); only invalid-ciphertext errors are crypto failures; the AWS error code is logged; all 5xx domain errors are now logged with the request ID.
3. `seed-demo` with a short password left a half-created tenant that could not be re-seeded: the password and existing tenants are checked before the first write, each tenant's secrets are printed as soon as it exists, and seeded tokens are attributed to the seeder in the audit log.
4. Behind a reverse proxy the per-IP login limit became one shared limit: per-IP and per-account limits are now separate (60 and 10 per minute), the account key is hashed to a fixed size, the 429 message is about sign-in, and `securedb serve --forwarded-allow-ips` exists.
5. Docs said every tenant table is under row-level security; the `tenants` registry is not. Corrected in the README and threat model, with the other inaccuracies (audit of rejected requests, KMS associated data, nonce-limit wording, keychain-only master rotation, authenticator setup, proxy caveats).

Deferred minors: the rate limiter rebuilds its table under a lock once it exceeds 100k keys; attempts on a locked account are neither audited nor logged; the API does not audit scope rejections while the playground does; the KMS region is not derived from the key ARN; mypy and pip-audit do not cover the optional `boto3` extra; `securedb init` does not warn when the store is `kms`; `update_api_key_scopes` records only the new scopes; a fixed-window boundary inside the login-throttle test could make it flaky.
