# SecureDB Vault — Milestone 6 (Admin console) Plan

**Goal:** A server-rendered admin console for tenant owners and viewers: password + TOTP
login, server-side sessions, CSRF protection, strict security headers, and pages for the
overview, API keys and policies, audit log, keys/rotation, and a tokenize playground.

**Spec:** §4.2 (console), §3 (`console_users`, `console_sessions`), §1.7 (console attacks),
§6 (console security tests), §4.3 (`create-user`).
**Builds on:** M5 (`feat/m5-lifecycle`), stacked branch `feat/m6-console`. Compact plan.

## Decisions

| # | Decision | Why |
|---|---|---|
| C1 | **No JavaScript at all** (plain HTML forms, full page loads) instead of vendored HTMX; CSP `default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'` | Removes the whole XSS-via-script class and any third-party/vendored script supply chain; nothing in the console needs client-side behaviour. Spec deviation (HTMX), recorded for the ADR. |
| C2 | Login asks for **tenant, email, password**, then a TOTP code on a second step | Emails are unique per tenant (spec §3); knowing the tenant lets every lookup run under normal tenant RLS. |
| C3 | Passwords: argon2id (`argon2-cffi` PasswordHasher defaults); 5 failures lock the account for 15 minutes; unknown users still run a hash (no timing oracle) | Spec §4.2. |
| C4 | TOTP via `pyotp` (RFC 6238, 30 s, ±1 step); the secret is encrypted with the tenant DEK (`ValueCipher`, AAD bound to the user ID); a used code cannot be replayed within its window | Spec §3 `totp_secret_enc`; replay protection is cheap and expected. |
| C5 | Sessions: 256-bit random ID in a `__Host-` cookie (`HttpOnly; Secure; SameSite=Strict; Path=/`); only its SHA-256 is stored; 8 h absolute, 30 min idle; logout deletes the row | Spec §4.2; a DB dump yields no usable session. |
| C6 | Session lookup runs before the tenant is known, via a select-only RLS policy matching `app.session_hash` (same pattern as the API-key auth lookup) | Keeps `console_sessions` under forced RLS. |
| C7 | Every state-changing request is POST with a per-session CSRF token checked in constant time; the pre-login forms use a signed double-submit token | Spec §4.2. SameSite=Strict is defence in depth, not the only control. |
| C8 | Roles: `owner` may create/revoke keys, change policies, rotate keys; `viewer` is read-only (403 otherwise) | Spec §4.2. |
| C9 | Security headers (CSP, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, HSTS on HTTPS) on **every** response, API included | Spec §4.2. |
| C10 | Console actions are audited with `Actor.console_user(user_id)`; login success/failure/lockout too | Every privileged action is attributable. |
| C11 | `reencrypt` also re-encrypts console users' TOTP secrets | Spec §2.5 note in M2. |

## Tasks

1. Migration 0007 + models (`console_users`, `console_sessions`, RLS incl. session-lookup policy, grants); security-headers middleware.
2. `securedb/console/auth.py`: create user (CLI `create-user` prints otpauth URI once), password + TOTP verification, lockout, sessions (create/lookup/touch/expire/logout), CSRF helpers.
3. Console routes + Jinja2 templates: login, TOTP, logout, overview, keys & policies, audit (+ verify with anchor), keys/rotation, playground; role checks; CSRF on every POST.
4. Re-encrypt TOTP secrets in `reencrypt`.
5. Security tests: CSRF missing/wrong → 403; login needs TOTP; lockout; session expiry (idle/absolute); viewer cannot mutate; headers present; templates auto-escape (XSS payload in key name); cookies flags.

## Review outcome

Fresh whole-branch review: 0 Critical, 5 Important, 12 Minor. Fixes were committed on `feat/m7-polish` (the next stacked branch), test-first.

Fixed:
1. Password hashing ran inside a database transaction (holding a pooled connection and a row lock for ~100 ms) and login was unthrottled, so anonymous login floods could starve every tenant: the hash now runs with no connection held, logins are rate limited per client IP and per account (`SECUREDB_LOGIN_ATTEMPTS_PER_MINUTE`, default 10), and attempts on an already-locked account no longer write audit entries.
2. No recovery from lockout: `securedb unlock-user` (audited). The lockout-as-DoS trade-off is documented.
3. Spec §4.2 "edit scopes" was missing: `update_api_key_scopes` + console form (audited).
4. The playground ignored the selected key's scopes: it now applies the same scope gate as the API and audits the rejection.
5. (Minor, fixed) Non-ASCII digits in a TOTP code or CSRF token raised a 500.

Recorded as a deliberate deviation (see ADR 0006): the console queries models directly instead of going through a service layer (spec §2.3).

Deferred minors: small residual timing differences between unknown tenant / unknown user / wrong password; TOTP guessing is bounded only by the lockout (5 per 15 min); expired session rows are deleted only when presented; locking an account does not end its existing sessions; pre-login CSRF token is an unsigned `__Host-` double-submit (plan said signed); console 403/404/422 render as JSON; the Encryption page's usage count omits TOTP secrets and shows no re-encryption progress; TOTP AAD constants are duplicated in `rotation.py`; a few route-level test gaps; CSP exemption for `/docs` is a prefix match; HSTS behind a TLS-terminating proxy needs `--proxy-headers`.
